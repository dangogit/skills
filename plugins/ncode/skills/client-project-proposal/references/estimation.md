# Estimation for agent assisted delivery

An estimate is engineering judgment, grounded in current scope, inspected samples, familiar tools and comparable delivery evidence. Distinguish planning targets from fixed-price commitments.

## Work and price

Estimate deliverable slices including risky integration proof, foundation/permissions, data handling, central workflow, document processing, QA, deployment and adoption. Combine shared setup rather than charging full frontend/backend/integration allowances for every feature.

For coding agents, distinguish fast generation from external proof. Familiar UI, CRUD and test scaffolding can run in bounded parallel tasks. Permissions, integration access, third-party acceptance, semantic accuracy and adoption still need evidence. Use actual permitted concurrency; do not count agent tokens as human days or apply a universal AI discount.

State the day unit and person/team basis. Active work, customer waiting time and calendar weeks differ. Parallelism can shorten elapsed time without reducing effort equally. A revised estimate needs a reason: narrower scope, proven tooling, different delivery model or corrected double counting. Do not shrink days merely to hit a target price or defend earlier judgment as measured fact.

Use current pricing direction or an explicitly sourced comparable. Do not inherit another client's rate, maintenance package, currency, warranty or payment terms automatically.

Daily pricing equals milestone days times rate, with reserve included once. Options and recurring fees are separate. A fixed price may differ from day-rate multiplication only as an explicit commercial choice. The helper validates totals; it does not choose fair rates or estimate effort.

## Milestones and uncertainty

Prioritize the client's pain. Each payment milestone has a visible delivered outcome and acceptance condition. Reserve alone is not an independent customer acceptance milestone.

Check API availability, template variants, migration and hosting restrictions before giving firm prices for them. For remaining unknowns, use bounded assumptions, an optional estimate or discovery milestone. Resolve scope changes before performing extra work.

Include the complete expected delivery lifecycle. A generated demo is not live acceptance; a fixture gate is not real-provider or original-file proof.

## Stack and recurring costs

Prefer the user's familiar stack when appropriate, verifying relevant current projects rather than prescribing one architecture for all clients. Familiarity does not grant rights to another client's code or data.

Verify current primary documentation for API behavior, fees, retention and residency. Separate application users from deployment seats, production from staging, database backup from file backup, and storage region from all processing locations.

Give infrastructure as a planning budget with volume assumptions and known baseline. Separate support fees from usage. Do not claim zero retention, processing-location guarantees or compliance beyond evidence. Do not buy services while preparing a quote.
